Agent Framework Assessment

I found a solid working list. I'd keep TypeScript frameworks separate from Python and .NET options because embedding them in Chamber has very different packaging costs.

Native TypeScript candidates

  1. Vercel AI SDK 7

    • What it already handles: ToolLoopAgent, streaming, tool execution, loop control, typed runtime context, MCP, many model providers.
    • Initial read for Chamber: Strong candidate. Small conceptual model and a natural fit for Electron. Its new HarnessAgent can even run established harnesses such as Pi, Codex, and Claude Code. Durable sessions and account login would need closer inspection.

  2. Mastra

    • What it already handles: Agent loop, tools, model routing, memory, MCP, human approval, workflows, multi-agent systems.
    • Initial read for Chamber: Strong candidate if we want a more complete runtime. More framework than Vercel AI SDK, but much less Chamber code may need rebuilding.

  3. LangChain JS and LangGraph JS

    • What it already handles: Agent loop, broad provider support including Ollama, middleware, MCP, persistence, checkpoints, human approval, multi-agent graphs.
    • Initial read for Chamber: The mature, feature-heavy option. It probably covers almost everything, but dependency size and abstraction overhead deserve scrutiny.

  4. Pi Agent Core and Pi AI

    • What it already handles: Stateful loop, streaming events, tool execution, approval hooks, cancellation, context transforms, provider normalization and unusual OAuth support.
    • Initial read for Chamber: Strong fit for Chamber's current event-driven design. Smaller and more direct than LangChain. The high-level harness remains the uncertain part.

  5. OpenAI Agents SDK for TypeScript

    • What it already handles: Agent loop, tools, handoffs, guardrails, sessions, MCP, tracing, custom ModelProvider interface.
    • Initial read for Chamber: More provider-pluggable than its name suggests. Still OpenAI-shaped, so we would need to test Ollama, Anthropic, and Google behavior through custom providers or its AI SDK integration.

  6. Google ADK for TypeScript

    • What it already handles: Agent loop, tools, MCP, sessions, sequential and parallel agents, routing, A2A, browser and Node builds.
    • Initial read for Chamber: Technically impressive and Electron-compatible. Google is the center of gravity, so provider neutrality and non-Google auth need testing.

    Struck from consideration: the TypeScript package is Google-first and does not provide the multi-provider account login Chamber needs.

  7. VoltAgent

    • What it already handles: Agents, tools, provider adapters, memory, MCP, subagents, workflows and observability.
    • Initial read for Chamber: Worth investigating. TypeScript-first and broad, though its smaller ecosystem makes maintenance risk more relevant.

  8. LlamaIndex.TS

    • What it already handles: Tool-calling loops, streaming events, workflows, structured output and multi-agent handoffs.
    • Initial read for Chamber: Viable, especially if Chamber grows stronger document and retrieval features. Its design leans more toward workflows and data applications than a desktop coding assistant.

Cross-runtime candidates

These are real contenders, but Chamber would need to ship another runtime or run a sidecar process.

  1. PydanticAI

    • Runtime: Python.
    • Initial read: One of the strongest cleanly designed agent frameworks. Broad models, MCP, durable execution, tools, approval flows and typed dependencies. The Python packaging cost is its main drawback.

  2. Microsoft Agent Framework

    • Runtime: Python, .NET and Go.
    • Initial read: Very complete. Agents, sessions, middleware, MCP, human approval, workflows, Ollama and several hosted providers. It is the successor to both AutoGen and Semantic Kernel. No matching TypeScript runtime currently appears in the official framework docs.

  3. Agno

    • Runtime: Python.
    • Initial read: Batteries included. Agent loop, 30-plus providers, sessions, memory, compression, MCP, approval pauses, teams, workflows and scheduling. A plausible replacement for much of Chamber's service code.

  4. LangGraph Python

    • Runtime: Python.
    • Initial read: The deeper and more established version of the LangGraph runtime. Strong persistence, interruption, resume and human approval support.

  5. OpenAI Agents SDK for Python

    • Runtime: Python.
    • Initial read: More mature than the TypeScript edition, with tools, handoffs, guardrails, sessions and MCP. It retains the same OpenAI-centered concern.

  6. Google ADK for Python

    • Runtime: Python.
    • Initial read: The original and more mature ADK implementation. Broad orchestration and session support, but Google-oriented.

    Struck from consideration: Python has broader model support through LiteLLM, but it still does not provide provider subscription login or Chamber's multiple-account model.

  7. CrewAI

    • Runtime: Python.
    • Initial read: Strong task, crew and workflow orchestration with MCP and human review. It looks better suited to predefined teams and jobs than Chamber's interactive single-mind chat.

Projects I would not start with

  • AutoGen and Semantic Kernel remain usable, but Microsoft now calls Agent Framework their direct successor and publishes migration guides.
  • MCP Agent is interesting for MCP-heavy systems, but it is narrower than Chamber needs.
  • Smolagents is deliberately small and Python-only. Good library, weak match for replacing all Copilot runtime behavior.
  • The many tiny TypeScript "agent loop" repositories from the search have little adoption and no convincing session, approval, or maintenance story.

My first-cut serious pool is Vercel AI SDK, Mastra, LangChain/LangGraph JS, Pi, OpenAI Agents JS, and Google ADK JS. PydanticAI and Microsoft Agent Framework stay on the list if shipping a sidecar runtime is acceptable.
