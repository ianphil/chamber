Agent Sidecar Architecture Proposal

Plan proposal for replacing Chamber's direct dependency on the GitHub Copilot SDK.

Chamber should define its own small gRPC protocol and run agent frameworks behind sidecar processes. Each mind can have an isolated runtime while Chamber keeps control of credentials, approvals, observability, sanitization, and the renderer contract.

Framework-specific types must stop at the sidecar boundary. Replacing a framework should require a new server-side adapter, not another rewrite of Chamber.

Proposed architecture

Chamber renderer
       |
Electron main process
       |
Chamber Agent Protocol (gRPC)
       |
       +-- PydanticAI sidecar
       +-- Microsoft Agent Framework sidecar
       +-- future runtime sidecar

Inside each sidecar, a narrow adapter maps the Chamber protocol to the selected framework:

Chamber gRPC service
        |
Framework adapter
        |
Agent framework and model providers

The boundary

Chamber should own the protocol. It should describe Chamber's needs rather than mirror PydanticAI, Microsoft Agent Framework, LangGraph, or any other framework.

A first contract could use one bidirectional stream plus health and shutdown operations:

service AgentRuntime {
  rpc Connect(stream ClientMessage) returns (stream AgentEvent);
  rpc Health(HealthRequest) returns (HealthResponse);
  rpc Shutdown(ShutdownRequest) returns (ShutdownResponse);
}

Messages from Chamber

  • Start or resume a session.
  • Send a user prompt.
  • Approve or deny a tool call the sidecar is about to run.
  • Cancel the current turn.
  • Update session-scoped provider credentials.

Events from the sidecar

  • Text and reasoning deltas.
  • Approval requests for tools with side effects.
  • Notifications that the mind's durable state changed.
  • Agent and session status changes.
  • Usage and model metadata.
  • Checkpoints needed to resume a session.
  • Typed errors and completion events.

One runtime per mind

Each active mind can run in its own process. This isolates failures, dependencies, credentials, memory, and cancellation. Different minds could use different frameworks or framework versions without loading those runtimes into Electron.

Sidecars should start lazily. Chamber starts a process when a mind becomes active, keeps it warm while useful, and shuts it down after an idle timeout. Configured but inactive minds should not consume a permanent Python, .NET, or Go process.

Ownership

The sidecar boundary is a framework boundary. Framework types stop at the protocol so a framework can be replaced without rewriting Chamber. It is not a privilege boundary. A sidecar represents a mind, so it acts as that mind: it runs the mind's tools and writes the mind's durable state.

Chamber keeps

  • Mind identity, configuration, and stable session identity.
  • OS-keychain credential storage and account selection.
  • The consent channel: approving or denying a tool call before it runs.
  • Which tools each mind is given.
  • Observability, parameter redaction, and audit records.
  • Renderer event contracts and validation of anything Chamber displays.
  • Sidecar startup, health checks, restart policy, and shutdown.

The sidecar owns

  • The agent loop and framework-specific session state.
  • The mind's tools and their execution.
  • The mind's directory and the artifacts inside it.
  • Model calls, streaming, retries, and context management.
  • Framework-native memory, checkpoints, and orchestration.
  • MCP lifecycle where the chosen framework provides it.
  • Mapping framework events and errors into the Chamber protocol.

Security rules

Security is policy, expressed two ways: the user approves an action before it happens, and a mind is given only the tools it should have. A mind whose only tool is a sandbox runner cannot reach anything the sandbox does not expose, whatever the model decides.

  • The Electron main process is the only Chamber component that connects to a sidecar.
  • A tool with side effects does not run until Chamber returns an approval decision.
  • Restricting a mind's tool set is a first-class control, not a fallback.
  • Credentials remain in the OS keychain until Chamber supplies the selected account to an authenticated process.
  • Credentials are scoped to the mind and session. They never appear in command arguments or logs.
  • Protocol logging uses Chamber's existing redaction rules, and never logs raw tool arguments.
  • A sidecar cannot send events directly to the renderer.
  • Chamber validates anything it renders, regardless of which mind produced it.

Framework replacement

A framework adapter lives behind the gRPC implementation. It translates Chamber messages into framework calls and translates framework events back into the stable Chamber event model.

Replacing a framework means implementing this adapter and passing the same protocol tests. The renderer, approval UI, persistence model, and most Electron services should remain unchanged. Tools move with the adapter, because tools belong to the mind rather than to the host.

Implementation plan

  1. Define the smallest useful protocol

    Model one Chamber flow: start a session, stream a response, propose a tool call, approve it, return the result, cancel a turn, and resume the session. Do not add framework features that this flow does not need.

  2. Build one disposable sidecar spike

    Implement the contract with one cross-runtime candidate. Package it beside Electron and prove startup, health checks, bidirectional streaming, clean shutdown, and crash detection on Windows, macOS, and Linux.

  3. Add a Chamber runtime client

    Put process management and the generated gRPC client behind one service in Electron main. Keep generated protocol types out of the renderer and shared product contracts.

  4. Migrate one mind end to end

    Run a single-mind chat through the sidecar while preserving Chamber's existing UI events, approval gate, credential store, cancellation, and conversation persistence.

  5. Prove framework portability

    Implement a second small adapter or test double against the same contract. This verifies that the protocol describes Chamber rather than assumptions from the first framework.

  6. Restore product parity

    Migrate MCP, skills, context management, session recovery, observability, and multi-agent modes. Keep each feature behind the same Chamber protocol where possible.

  7. Remove the Copilot runtime

    Delete the Copilot SDK integration, bundled CLI, runtime preparation, Copilot authentication paths, and obsolete packaging rules only after the sidecar path passes the existing desktop, server, and packaged runtime checks.

Questions the spike must answer

  • Does one process per active mind fit within acceptable startup time and memory use?
  • Can the sidecar resume a session after Chamber or the sidecar restarts?
  • How should Chamber version and negotiate changes to the protocol?
  • Which framework can expose tool approval without fighting its execution loop?
  • Can the chosen runtime and gRPC dependencies be packaged reliably on all three desktop platforms?
  • Which provider account login flows are officially permitted for a third-party desktop application?

Success criteria

  • A mind streams responses through the gRPC sidecar inside packaged Electron.
  • Chamber can approve, deny, and audit every side-effecting tool call.
  • Cancellation and resume work across the process boundary.
  • Two minds can run independently, including with different providers or frameworks.
  • A sidecar crash is contained and reported without taking down Chamber or another mind.
  • No framework-specific type reaches the renderer or Chamber's persistent product model.
  • A second adapter can satisfy the contract without changing the renderer flow.

Recommendation

Start with the protocol and one representative sidecar. Keep the contract deliberately small. If that spike proves streaming, approvals, cancellation, resume, and packaging, the architecture gives Chamber a practical path away from the Copilot SDK without binding the product to its next framework.
